# PABLO 黑箱任务的持久 Lab / Meta 运行

本文保留原始执行入口的说明。需要 Meta→Lab 建议执行闭环、结构化 Scientific Memory 与真实外部文献检索时，使用新的 [PABLO 研究入口](pablo-research.md)；历史运行不要原地切换实现。

此入口将 PABLO 的原始分子黑箱优化任务接到 RSI-Lab 的持久 `Runtime`：Lab 提议分子与获准操作，Meta 调查运行问题，Controller 执行评分并保存事实、预算和恢复状态。它使用 RSI-Lab 的角色、命令和记忆机制，不是原始三角色 PABLO 算法的复现。比较结果时应同时报告任务、初始化与执行架构。

## 示例任务口径

- 以 100 条初始化分子观测开始，再获得 200 条新增有效评分。
- 模型使用 `gpt-6.1-sol`，reasoning effort 为 `medium`；Lab 和 Meta 分别拥有自己的持久原生会话和工作记忆。
- 运行的模型调用预算最多为 600 次，Lab、Meta 及失败尝试均纳入实际账本。新增有效评分上限为 200，初始 100 条单列。
- 新增有效评分来自本次运行中成功结算的真实 oracle 结果。分子须通过冻结的有效性与身份检查，分数须为有限数值；初始分子和此前已接纳分子的重复身份不能计为新增结果。
- 无效提议、重复分子、未执行请求、失败或未知调用均保留其状态，不用零分代替缺失值，也不计为新增有效评分。
- 得到 200 条新增评分表示完成约定的评价数量，不表示已找到全局最优分子或证明算法优于基线。

“200 轮”在这里按新增有效评分计数。Lab 决策次数、Meta 决策次数、评分尝试次数和新增有效评分数分别记录。`run-until-wait --max-steps 200` 中的 `max-steps` 只限制调度动作，混合包含模型和工具 Work，不能代替本任务的停止条件。

## 冻结输入与黑箱边界

使用新的独立运行目录，保存初始化数据、任务协议、oracle 版本和代码标识、模型配置、预算及来源 hash。既有运行结果、旧问题结论或通过标记不能作为新运行已经执行的证据。

对 Lab / Meta 交付的是允许观察的任务说明、分子身份与真实评分；oracle 的内部目标、隐藏参考或实现细节不应通过模型提示、能力描述或来源目录意外泄漏。宿主保存的实现 hash 用于复核，不赋予模型阅读 oracle 内部的权限。

在线生成的分子事先未知。如果 TaskPlan 使用评价位置作为 `items`，协议必须说明这些位置不是已知分子身份。宿主在派发前不可变地绑定评价位置、canonical identity 和 Work；绑定后的失败或未知结果不能被其他分子覆盖。任何额外尝试规则都必须在运行前明确。

初始化的 100 条记录与新增结果分别保存。若初始化分数来自已有文件，应保留原文件及来源；若由本次程序实际计算，应另记初始化计算成本。不能把已有搜索得到的结果重新标记成未经搜索的初始化。

## 持久执行

从仓库根目录使用已安装任务依赖的 Python 执行。准备新运行不会调用模型；`--root` 必须指向尚不存在的绝对路径，`--initial-data` 指向原始初始化 CSV。默认运行身份为 `pablo-200`。

```sh
python scripts/run_pablo_rsi.py \
  --root /ABSOLUTE/PATH/TO/NEW-RUN \
  --initial-data /ABSOLUTE/PATH/TO/INITIAL.csv \
  --new-evaluations 200 --model gpt-6.1-sol --effort medium \
  --prepare-only

python scripts/run_pablo_rsi.py \
  --root /ABSOLUTE/PATH/TO/NEW-RUN --resume
```

恢复沿用已冻结模型与任务配置；更换模型必须创建新的运行目录。运行日志写入 `host-events.jsonl`，进度写入 `progress.json`，需要处置时写入 `attention.json`，完成评价数量后保存 `result.json` 和 `observations.json`。

宿主 runner 负责实际评分进度、输入准入、单 writer 锁和停止条件；通用 Runtime 负责 Work、Effect、Lab / Meta 会话、回执和证据发布。调用过程为：

1. 冻结运行配置与 TaskPlan，登记初始化事实，创建初始 Lab Work。
2. Lab 通过注册的评分能力提出明确输入，Controller 在真实调用前登记 Effect 并预约资源。
3. 宿主验证分子、任务绑定、剩余额度及重复身份，再执行 oracle。
4. 原始评分回执落盘并结算后发布事实，推进 Lab continuation；新证据也会创建 Meta discovery。
5. 每次推进后根据账本重新计算进度，并保存可审计的状态快照。

模型不直接调用科学工具或修改评分事实。`working_memory_delta` 保存该角色的计划、尝试与未决问题；它不作为评分表或完成数量的权威。历史会话中的信息也不能代替本轮来源交付。

每条新评分事实可以触发 Meta 检查，所以 Meta 调用量应单独预算。`max_open_reviews` 只限制定期开放检查，不会抑制由新证据触发的检查。Meta 提出的建议、能力请求或试验计划必须经过明确交付和执行；它的私有记忆不会自动改变 Lab 的策略。

达到新增评价目标后，宿主最多补做最终评分批次已创建的那一次 Meta discovery，再停止新调用。最终报告仍列出待处理工作、问题和 `meta_review_pending`，不把完成评价数量描述为全部科研问题已经解决。

## 输出与检查

通用运行目录保留以下产物：

| 路径 | 用途 |
| --- | --- |
| `ledger.sqlite3` | Work、Effect、预算、事实、会话、工作记忆和检查点 |
| `objects/` | 按内容 hash 保存的不可变输入、结果及事件对象 |
| `calls/<effect_id>/` | 模型输入、schema、原始 stdout/stderr、逐事件日志和回执 |
| `agents/<session_id>/workspace/` | 该原生会话的独立工作目录 |
| `receipt_<effect_id>.json` | Effect 结算前已经持久化的真实回执绑定 |

模型日志应位于 `calls/`，与 `Runtime.recover()` 的恢复路径保持一致。原生 Codex 会话和认证仍由使用者的 Codex 配置目录管理，不复制认证材料到实验目录。

初始化数据、运行账本、原始调用与实验报告由运行者本地保存，不随本仓库发布。上述文件名描述运行时产物，不表示仓库包含可直接续跑的历史实验。

检查时至少分别展示初始化观测数、新增有效评分数、无效/重复提议数、失败/未知 Effect、Lab / Meta 实际调用数、资源消耗和当前停止或等待原因。优化曲线只能使用真实已接纳评分，并保留达到相应结果前的消耗。

## 恢复与上下文容量

正常重启先取得该运行的唯一 writer 锁，再恢复已落盘回执和未完成发布。已经完成的评分与模型调用不因宿主重启而重做。没有可靠终态的 Effect 保持 unknown，不能依据进程消失、超时或等待时间重发。

Lab 与 Meta 通过精确的 `provider_thread_id` 续接。正常运行不使用 `--last`，也不使用 `--ephemeral`。每个角色的当前工作记忆与原生历史分别保留。

当前 CLI 后端按可观察原生 rollout 的完整字节加本轮请求检查容量。长跑可以按预先记录的容量策略，在当前角色为空闲且没有活动 turn 的边界创建 checkpoint 并显式 rebuild。重建保留 owner 和当前工作记忆，记录 lineage，旧 session 保持只读；不能通过重建清零消耗、绕过未知调用或重新执行评分。

如一个调用已经留下未知结果、未确认退出的 writer 或未完成对账，应先解决这些义务。若 Work 已因容量或上下文检查而 blocked，重建会话不会自动重新排入该 Work，宿主须记录原因并显式重新规划。单个新请求本身过大时，重建也不会解决问题。

队列暂时为空、`no_action`、等待用户回答或缺少能力都不等于已经获得 200 条评分。此时保存真实状态和具体依赖，不通过空转补齐轮数。

## CLI 验证边界

已使用 `codex-cli 0.163.0` 做过不调用模型的兼容性检查：transport 构造的新会话与精确 ID resume 命令均通过 `--help` 参数解析，使用的 feature 名称均存在。运行者仍需在自己的环境完成 CLI 安装与认证。

参数解析和登录状态不能证明模型可用或原生日志格式兼容。首个实际调用还需确认 `thread.started`、终态事件、用量记录、所属原生 rollout 与持久工作记忆提交；之后的首次 resume 需确认续接同一 thread。实际不兼容或超时须保留原始日志，按恢复规则处理。

通用会话、检查点和回执契约见[持久 Agent 使用说明](persistent-agents.md)。
