# Lab Team Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a run declare named sub-agent roles that Codex gives to the lead's sub-agents, record what each sub-agent was and did, and let the PABLO Lab decide each batch's role itself with a code backstop.

**Architecture:** The kernel (`rsi_lab/`) learns roles as part of the native settings it already freezes per run: it validates them, writes one role file per role before each call, names them on the Codex command and reads each sub-agent's role back from that sub-agent's own rollout. The PABLO host (`experiments/pablo/`) gains a second harness version in which the batch role comes from the Lab's request instead of the batch index, a decision record checked against the call's sub-agent record, and a `--team` preparation.

**Tech Stack:** Python standard library only in `rsi_lab/`; `unittest`; RDKit in the PABLO host; Codex CLI 0.163.0.

**Spec:** `docs/superpowers/specs/2026-11-18-lab-team-design.md`. It builds on `docs/superpowers/specs/2026-11-17-native-codex-capabilities-design.md`.

## Global Constraints

- A role with no declared roles, and a run with `subagents` off, sends the same Codex command, prompt and envelope as at this branch's base, and its Effect metadata and its receipt's `native_capabilities` are unchanged. The new `child_threads` fields of Task 3 appear for every call that used sub-agents, with or without roles.
- A PABLO run prepared without `--team` behaves exactly as today. Harness version `pablo_local_challenge_v1` and its 16 tests in `experiments/pablo/tests/test_harness.py` stay untouched and passing.
- Role name: full match of `[a-z][a-z0-9_-]{0,31}`, not `default`, `explorer` or `worker`, and not a fixed key of Codex's `[agents]` table (`max_depth`, `default_subagent_model`, `default_subagent_reasoning_effort`, `max_concurrent_threads_per_session`, `enabled`, `interrupt_message`). At most 8 roles. `description`: 1 to 300 characters, one line. `instructions`: 1 to 8,000 characters, not blank.
- A role file holds exactly `name`, `description` and `developer_instructions`.
- Backstop setting `challenge_backstop_batches`: an integer 1 to 100, or `None` for off; default 4. `decision.reason`: one line of 1 to 300 characters.
- Team architecture id `pablo_research_pr4_team_v1`; led harness version `pablo_lab_led_v1`.
- Team defaults: `max_effective_context_bytes` 4,194,304 and `prospective_rebuild_history_bytes` 3,145,728 (changed from 4,194,304 by the final review: the rebuild must come before a request can be refused for size).
- `rsi_lab/` imports the standard library only.
- No task runs `codex`, makes a model call, installs a package or uses the network. Tests build their own fixture Codex homes in temporary folders.
- Nothing opens, lists or scans `~/.codex/sessions` or `~/.codex/archived_sessions`. Code locates a rollout only by the exact path a call record names or by exact thread id through `codex_ledger._rollout_of`.
- The repository is public. Every id, path, account value and query in tests and documents is invented. Real rollouts carry `creator_user_id` and `creator_account_id`; no fixture copies such fields from a real record.
- What a sub-agent reports is a lead, not evidence; the existing prompt sentences on that stay.

- Kernel: `python3 -m unittest discover -s tests/v2` (901 pass at the base), `-s tests/generic` (59), `-s tests/literature` (185).
- Harness and team helpers: `PYTHONPATH=experiments/pablo:. "$PABLO_PY" -m unittest experiments.pablo.tests.test_harness` (16 pass at the base). `PABLO_PY` is a local interpreter that has RDKit and no `guacamol`; its path is given in each task's brief and is not written into the repository.

## What the live probe established

Run on 2026-11-18 with Codex CLI 0.163.0: five lead calls at low effort in a scratch run folder, with the kernel's own command plus the role flags. Ids below are invented stand-ins.

1. **Custom roles work in `codex exec`.** With `--ignore-user-config`, `-c agents.<name>.description="…"` and `-c agents.<name>.config_file="<absolute path>"` are enough. The spawn tool then lists the role with that description beside the built-ins `default`, `explorer` and `worker`.
2. **The role file reaches the sub-agent.** A file holding `name`, `description` and `developer_instructions` is delivered to the sub-agent as a `developer` message, whether or not the lead's history is forked.
3. **The spawn tool** is `spawn_agent` (namespace `collaboration`) with parameters `task_name`, `agent_type`, `fork_turns`, `message`, `model`, `reasoning_effort`. The lead's rollout records the call as a `response_item` of type `function_call`; `agent_type`, `task_name` and `fork_turns` are in clear in `arguments`, `message` is encrypted. Its output is `{"task_name":"/root/<name>"}`.
4. **The sub-agent's own rollout names its role.** Its first `session_meta` has `agent_role` (for example `"challenge"`), `agent_nickname`, `agent_path`, `parent_thread_id`, and the same three under `source.subagent.thread_spawn`. A sub-agent started without `agent_type` has no `agent_role` key. Built-in roles are recorded the same way (`"explorer"`, `"worker"`).
5. **History.** Without `fork_turns` the sub-agent starts with the lead's whole conversation: its first `session_meta` then has `forked_from_id` (the lead's thread id) and `subagent_history_start_ordinal`, and a second `session_meta` follows. With `fork_turns: "none"` neither is present and the sub-agent sees none of the lead's conversation.
6. **A start is recorded in the lead's rollout** as `event_msg` / `item_completed` with `item` `{"type":"SubAgentActivity","kind":"started","agent_thread_id":…,"agent_path":"/root/<name>","model":"<model>","reasoning_effort":"<effort>","id":"<the spawn call's call_id>"}`. A `completed` item follows with `model` and `reasoning_effort` `null`.
7. **Addressing a sub-agent again in a later turn** uses `followup_task` with `target`. The lead's rollout records `SubAgentActivity` of kind `interacted` with the same `agent_thread_id` and `agent_path` and `null` model and effort. The sub-agent keeps its role and its own history; its new usage row carries the new lead turn as `root_turn_id`. The other sub-agent tools are `send_message`, `wait_agent`, `list_agents` and `interrupt_agent`.
8. **Permission profile.** With the terminal on, a role sub-agent's `turn_context.permission_profile` holds the same deny entries for the run root and the Codex home as the lead's. Codex itself still reads a role file that lies inside the denied run root.
9. **Built-in roles do not change the model or effort**: `explorer`, `worker` and a sub-agent with no role all ran on the lead's model and effort. The lead can set `model` and `reasoning_effort` on any spawn; the `started` item records what was used.
10. **An unknown `agent_type`** makes `spawn_agent` return the text `unknown agent_type '<name>'`. No sub-agent starts, no `SubAgentActivity` is written and the turn continues.
11. **A sub-agent's web search** is recorded in its own rollout as `event_msg` / `item_completed` with `item` `{"type":"Extension","kind":"web.search","query":"<text>","action":{…},"results":[…]}`, the event carrying the sub-agent's `turn_id`. The kernel's earlier probe also saw items of type `WebSearch`; both shapes are read.

Items 1 and 2 hold, so approach A of the design is built and the fallback is not needed.

## Review Focus

1. **Settings stored before roles existed.** A run prepared at the base stores `subagents` as `{"max_concurrent": n}`. Resumed on this code it must validate to the same object, send the same request and command, and not be reported by recovery as having changed settings. Tests in Tasks 1 and 2.
2. **Role text that is awkward for TOML and the command line.** Quotes, backslashes, `=`, `#` and line breaks in `instructions`, and quotes in `description`, must reach Codex unchanged. Tests in Tasks 1 and 2 parse the written file with `tomllib`.
3. **Challenge addressed again instead of started.** When the Lab continues an earlier Challenge thread, the call record must still show a `challenge` sub-agent, with `started_in_call` false and only this call's tokens, and the dispatch check must accept it. Tests in Tasks 3 and 5.
4. **A sub-agent whose role cannot be read.** A child with `role` `None`, or a call with no `child_threads` at all, must make a claim of "dispatched" fail with a message that says why, and must not fail a claim of "not dispatched". Test in Task 5.
5. **The edges of the backstop.** Inherited stagnation must not arm it; a challenge batch in which no candidate was scored must not satisfy it; it must fire exactly at the limit and never when off. Tests in Task 5.

**Role text.**

**`GOAL`** says, in this order: the Lab leads a team and may start `local`, `challenge` and `default` helpers; they only propose, and what they return is a lead; only the Lab requests `pablo.select_candidates` and `pablo.evaluate`; for every batch the Lab decides whether to ask Challenge and which proposal to run and states it in the request's `decision` (`challenge_dispatched`, `challenge_adopted`, `reason`); when the harness context's `required_role` is `challenge` it must dispatch Challenge and run its proposal; it should start Challenge with `fork_turns` `none` and pass it the anchors, constraints and results it needs. It replaces the sentences of today's goal text that describe the fixed local/challenge schedule; the rest of the goal text is unchanged.

**`native_block`** takes the parsed `--native-capabilities` file and returns the block for the run config. It refuses: a file where `lab.subagents` is off or missing; a file whose `lab.subagents.roles` names `local` or `challenge`; any role's `terminal.readable_roots` entry for which `exposes_objective` returns a reason. It adds `ROLES` to `lab.subagents.roles`.

**`exposes_objective(root, protected)`** returns a sentence naming the reason, or `None`. `protected` are the repository checkout, the frozen source copy and each parent run root. Reasons: `root` equals, contains or lies inside a protected path (by resolved path); a folder named `guacamol` holding `__init__.py` is found under `root`. The search does not follow symlinks, goes at most 6 levels deep and visits at most 20,000 folders; a root that exceeds either bound is refused as too large to check.

**`not_blind`** returns `Web search is on for the Lab: the hidden objective is protected by instruction only, and this run is not a blind run.` when `lab.web_search` is true, else `None`.
