# Meta 调整 Lab 编排：效果信号、策略版本与试用发布（设计）

日期：2026-11-10　状态：待用户审阅　基线：`af55640`（分支 `claude/rsi-agentic-review-16b253`）

实现方式沿用仓库现状：只用 Python 标准库，所有状态变更走 `Store.mutate`，新机制由运行配置里的一个开关启用。

## 1. 摘要

**要解决的问题。** 现在 Meta 看不到 Lab 的过程数据（每一步做了什么、被拒了几次、是否在重复请求、花了多少）。Lab 的编排（指令、上下文、巡检间隔）写死在代码和冻结配置里。Meta 即使判断出 Lab 在空转，也没有可以改的对象，更没有让改动生效或回退的机制。[系统设计](../../system-design.html) §2、§7、§11 描述的“Lab 执行 → Meta 发现 → 调查 → 修改 → 小范围验收 → 发布 → 续跑”尚未实现。

**做完之后。** 在运行配置里声明 `orchestration` 后：

1. 控制器按固定步数的窗口统计 Lab 的过程指标，写成账本事实。指标越过冻结阈值，或 Lab 因自己的输出被拒、请求的工具明确失败而停下时，控制器用现有的 `coded_anomaly` 触发类型唤醒 Meta 发现，并把这条事实完整交给它。
2. Lab 可调的编排面成为一个带版本的策略对象。运行时读取“当前生效版本”，每个 Lab/Meta 请求包和 Effect 都记下所用版本。
3. Meta 在处置模式下多一个动作 `propose_policy_change`，直接提交一份完整的候选策略。只有引用了控制器测出的越线事实，提议才会被接纳。
4. 候选策略先试用一个窗口。窗口没有越线就保留；越线、Lab 再次停下或超时就回退。保留还是回退由代码按冻结阈值决定，模型不参与。
5. `settle_trial` 的判定改为考虑噪声，`minimum_pairs` 开始起作用。

不声明 `orchestration` 的运行里，前四项都不存在，行为和请求包字节与现在一致。第 5 项与这个开关无关，对所有运行生效。

**本次不做。** 工具自主构建（原计划第 3 期）、OS 级沙箱、模型 effort 的调整、基于 `TaskPlan` 进度或指标平台期的检测、策略的成对对照试验。理由见 §3。

**你已确认的四项。**

1. Meta 可改的字段：Lab 指令的补充段、交给 Lab 的上下文（最近的已核验结果、最近几步的过程摘要）、巡检间隔。任务目标、阈值、预算、验收判据、Meta 自己的指令和权限不可改。模型 effort 本次不做。
2. “显著没效果”由控制器按窗口计算，阈值冻结在运行配置里，使用账本里现在就能算出的五个指标。
3. 模型写的工具代码仍需人工按 hash 授权，直到有 OS 级沙箱。
4. 本次做效果信号、策略对象与试用发布，以及 `settle_trial` 判定规则修正；工具自主构建另起一个变更。

## 2. 现状与缺口

以下均已在 `af55640` 的代码中核对。

| 缺口 | 现状 |
| --- | --- |
| 看不见 | `Runtime.observe` 只在 `publish_adapter_effect` 里以 `new_evidence` 触发。`Runtime._context` 给 Meta 的只有事实，没有 Lab 的步骤、被拒提议、重复请求和成本。`build_report` 的结果只进了驱动的返回值 |
| 没有可改对象 | Lab 指令和动作白名单是 `roles.py` 里的常量。运行配置在 `init` 时冻结。试验规格里的策略版本只是一个字符串 |
| 改了也不生效 | 没有代码读取 `settle_trial` 的 `version_action`。`propose_trial` 的 `plan_ref` 必须指向宿主事先存好的规格，模型自己提交不了 |
| 判定规则 | `settle_trial` 用“成对增益均值 ≥ `min_gain`”，不考虑噪声。所有登记的臂都必须到齐，`minimum_pairs` 因此不起作用 |

`TaskPlan` 进度不在账本里（`select_items` 是宿主调用的纯函数）。模型 effort 冻结在会话的 `runtime_binding` 里（`agent_state.py` 的 `ensure_session`），改它必须重建会话。这两点决定了本次的范围。

## 3. 目标、非目标、反目标

**目标**

- G1 Meta 能拿到控制器计算的、有来源的 Lab 过程数据。
- G2 Lab 没有效果时，Meta 不需要宿主介入就会被唤醒。
- G3 Meta 能在封闭的字段范围内修改 Lab 的编排，改动先小范围试用，由代码决定保留或回退。
- G4 任何一次模型调用用了哪个策略版本，都能从账本查到。
- G5 试验结算不再把纯噪声判为达标。

**非目标**

- 工具自主构建，以及让模型写的代码无人值守地执行。
- 调整模型 effort、模型型号、Lab 的动作白名单或基础指令。
- 检测“每轮都有新结果但指标不涨”。这需要宿主声明一个有方向的进度指标，另行设计。
- 证明策略变更带来了科研收益。试用发布只是工程验收，结果里固定写明 `benefit_claim: not_evaluated`（系统设计 §11.5、§12）。
- 用 `TrialEngine` 对两个策略做成对对照。目前没有能在隔离分支里按某个策略运行 Lab 的执行器。`settle_trial` 的 `version_action` 在本次之后仍然没有消费者。
- 按分支或按 Lab 实例设置不同策略。策略指针是整个运行共用的。

**反目标**（出现任何一条即视为失败）

- 一个变更改得动批准它自己的判据。
- 模型的说法（“我测过了”“有效果”）能让策略生效或保留。
- Meta 被自己触发的信号反复唤醒，调用次数没有上限。
- 未声明 `orchestration` 的运行，在 §5.10 的试验判定之外出现任何行为变化。
- 为了算指标而重发 Effect，或把结果未知的调用当成已结束。

## 4. 必须保持的约束

- Effect 至多派发一次；结果未知的调用在对账前保持未知，包含它的窗口不结算。
- 所有状态变更走 `Store.mutate` 并带幂等键，重放得到同一结果，`verify_history` 通过。
- 判据（窗口大小、阈值、次数上限、字段上限）只存在于不可变的运行配置里。策略对象里没有任何判据字段。
- 只用标准库。
- 代码注释、提交信息用英文；面向使用者的文档用中文。

## 5. 设计

### 5.1 开关与冻结配置

运行配置新增一个键 `orchestration`。没有它，下面所有机制都不存在。有它时，`Runtime.__init__` 和命令行 `init` 都按下表校验（与 `unknown_usage_policy` 的做法相同），出现未登记的键即拒绝。

```json
"orchestration": {
  "window_steps": 8,
  "thresholds": {
    "min_new_results": 1,
    "max_rejected_fraction": 0.5,
    "max_repeat_fraction": 0.5,
    "max_tool_failure_fraction": 0.5,
    "max_tokens_per_new_result": 200000
  },
  "max_triggers": 3,
  "max_changes": 2,
  "release_timeout_seconds": 3600,
  "baseline": {"lab_step_digest": 4},
  "limits": {"lab_guidance_chars": 2000, "lab_recent_results": 8, "lab_step_digest": 16,
             "open_review_interval_batches": [1, 20]}
}
```

| 键 | 必填 | 含义 |
| --- | --- | --- |
| `window_steps` | 是 | 一个窗口包含多少个已结束的 Lab 步骤，2 到 64 |
| `thresholds` | 是，至少一项 | 见 §5.2。没写的阈值不参与判定 |
| `max_triggers` | 是 | 整个运行中，信号最多唤醒 Meta 发现多少次，0 到 100 |
| `max_changes` | 是 | 整个运行中最多发布多少次策略变更，0 到 20。0 表示 Meta 只能调查，不能改策略 |
| `release_timeout_seconds` | 否 | 试用的最长时间，默认取 `wait_timeout_seconds`，再没有则为 3600 |
| `baseline` | 否 | 初始策略里与默认值不同的字段 |
| `limits` | 否 | 各字段的上限。只能比内置上限更紧 |

运行配置在账本里不可变，并且是事件哈希链的起点，所以这些值在运行开始后改不了。已有的运行也因此不能中途启用这个功能。

它与 `research_features` 下的 `meta_lab`、`scientific_memory` 互不依赖，可以同时启用。

### 5.2 Lab 步骤与窗口

**步骤。** 一个 Lab 步骤是一次真正派发过的 Lab 模型调用，即一个 `kind='lab'` 的 Effect。按 Effect 的创建顺序排列。仅做最终复核的调用（`final_review_only`）和从未派发就被取消的调用不算步骤。

每个步骤从账本推出一个结果类别：

| 类别 | 判定依据 | 计入 |
| --- | --- | --- |
| `result` | 提议已应用，动作是 `request_diagnostic`，工具 Effect 成功且发布完成 | 新结果数；可能同时是重复请求 |
| `rejected` | 提议状态为 `rejected`、`blocked_stale`、`blocked_action`，或工具在执行前拒绝了输入（`_reject_diagnostic`） | 被拒 |
| `tool_failed` | 工具 Effect 为 `failed_definite` | 工具失败 |
| `no_action`、`issue`、`tool_cancelled` | 提议已应用，动作为 `no_action` 或 `propose_issue`；或诊断 Work 被取消 | 只计步数 |
| `provider_failed` | Lab 的模型调用为 `failed_definite` | 只记录，不构成越线 |
| 未结束 | Effect 为 `prepared`、`dispatching`、`unknown`，或费用未对账，或提议仍是 `admitted`，或工具与发布未完成 | 不计入 |

- **新结果数**：该步骤触发的那次适配器发布中，`facts` 里内容哈希（`content_ref`）在更早的事实中没有出现过的条数。
- **重复请求**：能力标识、版本、规范化后的输入，与本次运行中更早的某个 Lab 诊断请求完全相同，并且那个请求已经发布过结果或已被拒绝。更早的请求如果是工具失败，再试一次不算重复。

**窗口。** 步骤按“所用策略版本”分段，每段内每 `window_steps` 个连续的已结束步骤组成一个窗口。版本切换时，旧版本段里不足一个窗口的尾部不结算。窗口里只要有一个步骤未结束，这个窗口和它之后的窗口都等待。

**指标与阈值。**

| 阈值 | 越线条件 |
| --- | --- |
| `min_new_results`（整数 ≥ 1） | 窗口内新结果数小于它 |
| `max_rejected_fraction`（0 到 1） | 被拒步骤数 ÷ 窗口步数 大于它 |
| `max_repeat_fraction`（0 到 1） | 重复请求步骤数 ÷ 窗口步数 大于它 |
| `max_tool_failure_fraction`（0 到 1） | 工具失败步骤数 ÷ 窗口步数 大于它 |
| `max_tokens_per_new_result`（正数） | 新结果数 > 0 且 Lab 调用的 token 总量 ÷ 新结果数 大于它。有调用的 token 数缺失时不判定这一项，并在事实里写明 |

越线只是一个疑点。低产出和高成本可能来自任务本身的难度（系统设计 §7.2），所以越线之后是唤醒 Meta 去调查，而不是直接改策略。

工具明确失败会结束当前的 Lab 链（见 §5.3），所以一条链里最多出现一次工具失败。`max_tool_failure_fraction` 主要对反复启动 Lab 的宿主有意义；只有一条链的运行由停机事实覆盖。

### 5.3 信号事实与唤醒 Meta

**窗口事实。** 每个窗口结算时，控制器在一次 `Store.mutate` 里写入：

- 一条 `raw_fact`，`provenance` 为 `{"source": "controller_orchestration_signal", ...}`。内容包括：策略版本、每个步骤一行的记录（结果类别、动作、能力标识与版本、输入哈希与截断后的输入片段、是否重复、新结果数、截断后的拒绝原因、token 数）、汇总指标、冻结阈值、越线项列表。每行步骤记录有固定的字节上限。
- 一条 `registration`（`kind='orchestration_window'`），供查询与幂等判断，并记录这条信号的唤醒状态。

**停机事实。** 驱动找不到可运行的 Work 时做一次空闲检查。Lab 链已经结束，并且属于下面两种情况之一时，写入一条同样来源的 `raw_fact` 和一条 `registration`（`kind='orchestration_stall'`），越线项为 `lab_stopped`，并附上最近的步骤记录：

- `driver_report` 的 `stopped_lab` 表明 Lab 是因为自己的提议被拒（`rejected`、`blocked_stale`、`blocked_action`）而停下；
- Lab 最后一步请求的工具明确失败（`failed_definite`）。

第二种情况在现有代码里没有任何信号：工具明确失败后不会给 Lab 安排后续步骤，驱动报告是干净的 `quiescent`（已用临时脚本在 `af55640` 上复现）。本次不改变这一点，失败不会作为新步骤交回 Lab。Lab 之后恢复运行时（发布时的续跑，或宿主重新启动），可以从步骤记录里看到这次失败。

同一个停机状态只写一次：幂等键由“最后一个 Lab Work、它的提议和它的工具 Effect”算出，时间流逝或 Meta 自己的调用不会刷新它（系统设计 §7.1）。Lab 以 `no_action` 或 `propose_issue` 主动结束不算停机。

模型服务失败、被取消的调用、会话需要恢复、请求包超出容量，不产生停机事实。这些 Meta 改策略解决不了，仍按现状出现在驱动报告里。容量问题通常来自会话历史的增长，而策略只能增加上下文。

**唤醒。** 有越线项的信号，登记行标为“待唤醒”。每次 `advance()` 和空闲检查时，下面五条同时成立，就为最新的一条待唤醒信号唤醒 Meta，并把更早的待唤醒信号标为“被取代”：

1. 已唤醒次数小于 `max_triggers`；
2. 没有由编排信号引出的、尚未运行的发现 Work；
3. 没有正在处理中的编排 Issue。编排 Issue 指引用了信号事实且未关闭的 Issue；“正在处理”指它还有就绪或已租用的 Work、未结束的等待，或未结清的 Effect，也就是不在驱动报告的 `stalled_issues` 里。没有人接手的 Issue 不阻止唤醒；
4. 没有正在试用的策略，运行也没有进入收尾；
5. 这条信号仍然成立：窗口事实的策略版本等于当前生效版本；停机事实对应的停机状态没有变化。不再成立的信号标为“已失效”。

这样，在一个编排 Issue 处理期间出现的停机，会在该 Issue 结束后被重新考虑，而不是永远没人知道。唤醒通过 `Runtime.observe(event_id, 'coded_anomaly', 0, [事实])` 完成。`observe` 增加一个可选参数，把这条事实列为必需证据，保证它被完整交付而不是分页。Meta 发现拿到事实后走现有流程：`propose_issue`（引用这条事实）或 `no_action`。

空闲检查如果创建了新的 Work，驱动继续循环，Meta 发现会在同一次 `run_until_wait` 里运行。

**不干扰现有选取。** `observe` 在开放巡检时默认选取最近 16 条原始事实。信号事实不参与这个选取，避免过程数据挤掉科研事实。

### 5.4 策略对象与版本

策略对象的字段是封闭的：

| 字段 | 含义 | 默认 | 默认上限（内置最大值） | 修改面 |
| --- | --- | --- | --- | --- |
| `lab_guidance` | 追加在 Lab 固定指令之后的补充段；`null` 表示没有 | `null` | 2000 字符（4000） | T2 |
| `lab_recent_results` | 每个 Lab 请求包额外附带最近 N 条已发布的结果事实，作为可选证据 | 0 | 8（16） | T1 |
| `lab_step_digest` | 在任务约束里给 Lab 附上最近 N 步的过程记录，由控制器计算 | 0 | 16（32） | T1 |
| `open_review_interval_batches` | `observe` 的开放巡检间隔 | 运行配置里的现值 | [1, 20]（[1, 100]） | T1 |

修改面一栏对应系统设计 §11.1。Lab 的固定指令、动作白名单、`max_open_reviews`、预算、任务目标都不在策略对象里。每个字段是 0（或 `null`）到上限之间的绝对值，候选可以比宿主的 `baseline` 更低，例如撤掉补充段。策略能做的只是在控制器默认交付的内容之上增加上下文，拿不掉 Lab Work 本来就带的证据。

**版本。** 策略版本是策略对象规范 JSON 的 SHA-256。基线策略由运行配置算出（默认值加上 `baseline`），不需要事先写入账本。第一次发布变更时，基线和候选各写一条 `registration`（`kind='orchestration_policy'`），并建立唯一的指针行 `orchestration_active`，记录当前生效版本、已接受版本和进行中的发布。之后的切换都对指针行做版本比较（CAS）。

### 5.5 运行时如何使用当前版本

- **Lab 请求包**（`Runtime._context`）：`task.constraints.orchestration` 写入 `policy_version`；有补充段时写入 `lab_guidance`；`lab_step_digest > 0` 时写入最近步骤记录；`lab_recent_results > 0` 时把最近的结果事实加入可选证据。可选证据在容量紧张时由现有的包规划器分页或省略，不会让请求包无法表示。
- **Lab 指令**（`MetaAgent.arguments`）：固定指令不变，补充段追加在后面，并带一句固定说明：补充段来自已发布的策略某版本，不能授予动作、能力、预算，也不能改变任务目标；与前文冲突时以前文为准。
- **版本切换说明**：同一个 Lab 会话上一次调用所用的版本与本次不同时，请求包和指令里带一句固定说明：编排策略已切换到某版本，此前版本的补充段已撤回，只以本次请求中的补充段为准。上一次所用的版本从该会话最近一个 Lab Effect 的记录里读取。
- **Meta 请求包**：`task.constraints.orchestration` 写入当前版本、当前策略内容、字段上限、剩余变更次数、此刻是否可以提交变更、进行中的发布，以及最近几个窗口的指标与越线项。
- **处置请求包的必需证据**：现有代码里 Issue 的证据都是可选的，请求包放不下时会被分页或省略。Issue 引用了信号事实时，其中当前生效版本下最新的一条越线事实，以及该 Issue 最新的一条发布结果事实，改为必需证据。其余证据仍是可选的。
- **Meta 指令**：增加一段固定说明：信号事实是控制器的过程测量，越线是疑点不是诊断；`propose_policy_change` 的范围与限制；阈值、预算、任务目标、动作白名单和 Meta 自己的权限不可改；发布结果不是科研收益的证据。
- **Effect**：`prepare_meta` 在 Effect 的 `metadata.orchestration` 里记下 `policy_version`。适配器 Effect 也记下准备时的生效版本，便于归属。
- **执行前核对**：`CodexExecutor` 现在会核对请求包里的研究策略与 Effect 记录一致。对编排版本做同样的核对，不一致则拒绝执行。
- **巡检间隔**：`Runtime.observe` 改为读取当前策略的 `open_review_interval_batches`，并在返回的准入记录里写上所用版本。
- **最终复核**：`final_review_only` 的调用只记录版本，不附补充段和步骤记录。

### 5.6 Meta 提交变更：新动作与准入

处置模式新增动作 `propose_policy_change`，载荷是封闭的：

```json
{"base_version": "<当前生效版本>",
 "lab_guidance": "<文本或 null>",
 "lab_recent_results": 4,
 "lab_step_digest": 8,
 "open_review_interval_batches": 5,
 "rationale": "<为什么改>",
 "expected_observation": "<预期在试用窗口里看到什么>"}
```

载荷是完整的候选策略，不是差量。这样候选版本可以直接由内容算出，也不需要宿主事先存任何东西。`rationale` 和 `expected_observation` 只进入记录，不参与判定。

**何时出现在 schema 里。** 只有在构建处置请求包的那一刻“可以提交变更”时，这个动作才进入响应 schema。“可以提交变更”指下面第 1、2、4、5、8 条在那一刻成立（第 1 条此时检查的是 Issue 的证据里有这样一条事实）。`response_schema` 增加一个参数；`MetaAgent.arguments`、`validate_command`、`CodexExecutor` 三处按现有 `research_features` 的方式用同一个值重新计算 schema（`metadata.orchestration` 里同时记下这个布尔值）。发现模式和 Lab 模式的 schema 不变，最终复核时不出现。

**接纳条件。** 全部由代码检查。任何一条不满足，提议按现有路径记为被拒或被阻塞。现有规则下每个 Issue 一生只有一次修复机会，这里不改。

1. 命令引用的证据里，至少有一条在本请求包中完整交付的信号事实，它有越线项，并且是在当前生效版本下测出的。
2. `base_version` 等于当前生效版本，且没有正在试用的策略。
3. 候选通过封闭字段与上限校验，并且至少有一个面向 Lab 的字段（`lab_guidance`、`lab_recent_results`、`lab_step_digest`）与当前策略不同。巡检间隔可以一并修改，但不能单独修改：它只在宿主以 `batch_boundary` 调用 `observe` 时起作用，`run_until_wait` 和命令行都不发这种触发，用 Lab 的窗口也无法验收它。
4. 已发布的变更次数小于 `max_changes`。
5. 没有处于活动状态的试验（`TrialEngine` 的 `active`、`awaiting_settlement`、`restoring`）。
6. 同一对（基线，候选）没有在本次运行里被回退过。
7. 候选新增的必需内容（补充段字节数加上步骤记录的最大字节数）不超过请求包容量的四分之一。
8. 最后一个 Lab Work 没有因请求包超出容量而阻塞。这种阻塞需要操作者重建会话，策略改了也解决不了；此时发布只会让续跑步骤再次阻塞、试用立即失败。

第 1 条就是“有代码可核验的证据”这个要求的落点：没有控制器测出的越线，Meta 改不了 Lab 的编排。§5.5 把这条越线事实列为处置请求包的必需证据，保证第 1 条不会因为请求包变大、事实被分页而永远无法满足。

### 5.7 试用发布与结算

**发布。** 路由在一次 `Store.mutate` 里完成：复核上面与状态有关的条件、写入版本记录、写入发布记录（`kind='orchestration_release'`，状态 `provisional`，带截止时间和冻结判据的哈希）、把指针切到候选、变更计数加一。同一事务里，如果 Lab 链已经结束（没有就绪或已租用的 Lab Work，没有等待执行的 Lab 诊断，也没有未结清的 Lab 或工具 Effect），就补一个 Lab Work，输入取自最近一个 Lab 步骤的证据。随后按现有 `propose_trial` 的方式建立依赖并把 Issue 挂起，等待的截止时间晚于发布的截止时间。

截止时间由提议被接纳的事件时间加上 `release_timeout_seconds` 得出，与重试时刻无关。

**结算。** 试用窗口是“记录了候选版本的前 `window_steps` 个已结束 Lab 步骤”。发布之前已经准备好的 Lab 调用带的是旧版本，不计入。

| 情况 | 验收 | 部署 | 原因码 |
| --- | --- | --- | --- |
| 试用窗口结算且没有越线 | `passed` | 候选成为已接受版本 | `window_passed` |
| 试用窗口结算且有越线 | `failed` | 指针回到基线 | `window_breached` 与越线项 |
| 空闲检查发现 Lab 在候选版本下停机（§5.3 的两种情况），或发布之后 Lab Work 因请求包超出容量而阻塞 | `failed` | 指针回到基线 | `lab_stopped` |
| 到截止时间窗口仍未满，或运行进入收尾 | `incomplete` | 指针回到基线 | `insufficient_steps` 或 `run_finalizing` |

结算在一次 `Store.mutate` 里更新发布记录、版本记录和指针，并写入一条 `validation` 事实（`provenance.source = 'code_settlement'`）。Issue 仍打开时，把这条事实加入它的证据。随后更新依赖并 `tick`，Meta 处置被唤醒，读到结果后自行决定关闭 Issue 或在剩余次数内再提一个候选。这与 `publish_trial_outcome` 的做法一致。

结果记录对齐系统设计 §11.5 的 `ChangeOutcome`：`acceptance`、`deployment`、`reason_codes`、试用窗口的指标与事实引用、已观察步数与要求步数、冻结判据哈希，以及固定的 `benefit_claim: "not_evaluated"`。

**回退的含义。** 回退只切换指针，之后构建的请求包使用基线。已经用候选版本准备好、尚未派发的调用仍按原包执行，账本里的记录如实反映它用了哪个版本。候选版本下产生的科研事实、费用和回执全部保留并继续有效：策略改不了工具版本、输入准入和结果发布，所以这些结果的真实性与策略无关。回退之后不自动补 Lab 步骤。

回退抹不掉 Lab 已经读过的内容。真实运行里 Lab 的调用续接同一个模型会话，候选版本的补充段仍留在会话历史里，也可能已经写进它的私有工作记忆，而账本会如实记录之后的调用用的是基线版本。§5.5 的版本切换说明是缓解，不是消除。因此回退之后基线版本下的窗口，仍可能带有候选补充段的影响。本次不为版本切换重建 Lab 会话：重建会丢掉会话历史，带来的变化比补充段本身更大。

**已接受的版本不会到期回退。** 之后如果在它之下再次越线，按 §5.3 重新唤醒 Meta（受 `max_triggers` 限制）。

### 5.8 一个例子

1. Lab 请求了一个不存在的能力版本，提议被拒。修复步骤再次被拒。Lab 链结束。
2. 驱动空闲检查发现 `stopped_lab` 的提议状态是 `rejected`，写入停机事实，唤醒 Meta 发现。
3. Meta 发现读到两步的拒绝原因，提出 Issue 并引用这条事实。
4. Meta 处置提交 `propose_policy_change`，补充段写明要使用的能力版本和输入字段。代码核对全部接纳条件后发布：指针切到候选，补一个 Lab 步骤，Issue 挂起。
5. Lab 在候选策略下继续。八个步骤结束后试用窗口结算，没有越线，候选成为已接受版本。
6. Meta 处置被唤醒，读到 `acceptance: passed`，关闭 Issue。

如果第 5 步里 Lab 再次因提议被拒而停下，空闲检查立即回退并唤醒 Meta 处置。

### 5.9 接入点、崩溃恢复与幂等

**接入点。** `Runtime.orchestration` 在配置了 `orchestration` 时存在，否则为 `None`。`run_until_wait` 每轮循环开始时调用 `advance()`（结算到期的窗口与发布），在找不到可运行 Work 时调用空闲检查。`Runtime.finalize` 在登记收尾状态后也调用一次 `advance()`，让进行中的试用按“运行进入收尾”回退，不留下悬空的试用版本。`runtime.status()` 在启用时多一个 `orchestration` 键：当前版本、进行中的发布、窗口数与剩余次数。不经过 `run_until_wait` 的宿主（例如直接调用 `run_lab` 与 `execute_adapter` 的示例）需要自己调用 `advance()`。

**幂等键。**

| 操作 | 键 |
| --- | --- |
| 窗口事实 | `orchestration-window:<窗口标识>`，窗口标识由首尾步骤的 Effect 标识算出 |
| 停机事实 | `orchestration-stall:<停机状态签名>` |
| 唤醒 | `observe:<事件标识>`（现有方案），随后 `orchestration-wake:<信号>:<新状态>` 更新登记行 |
| 发布 | `route:<提议>:release`、`route:<提议>:dependency`、`route:<提议>:park` |
| 结算 | `orchestration-release-settle:<发布>`、`orchestration-release-dependency:<发布>` |

键对应的载荷只含标识，不含时钟。窗口内容、是否到期等判断在事务内部根据账本状态得出，并且先确认记录仍处于可变状态（与 `Controller.tick` 的做法相同）。因此在任意两步之间崩溃后重新运行，已提交的步骤返回原结果，未提交的步骤补做，不会出现第二次发布或第二次结算。信号的唤醒状态（待唤醒、已唤醒、被取代、已失效）记在它的登记行上，与不可变的事实分开。唤醒分两步：`observe` 创建发现 Work，然后把登记行标为已唤醒。两步之间崩溃时，下一次 `advance()` 发现 Work 已经存在，只补第二步。已唤醒次数按已创建的发现 Work 计数。

### 5.10 试验判定规则修正

改动只在 `rsi_lab/trials.py`。

**`minimum_pairs` 的含义。** 每个登记的臂仍然必须有一条测量记录（防止只报对自己有利的样本）。一对样本在两臂都 `complete` 且所有指标都有值时才“可评估”。可评估的对数不少于 `minimum_pairs` 时执行有效，不可评估的对被排除并在结果里逐条列出原因。此前任何一条不完整的记录都会让整个试验不完整，`minimum_pairs` 因此没有意义。

**完成性保护。** 如果某一对基线臂完整而候选臂不完整，证据不能判为 `met`。否则候选可以靠在困难输入上失败来抬高均值。

**证据规则。** 规格增加一个可选键 `evidence_rule`：

- 缺省或 `{"kind": "paired_lower_bound", "confidence": 0.95}`：对每个主指标，取可评估对的增益，计算单侧置信下界 `均值 − t(置信度, n−1) × 标准差 ÷ √n`，下界不低于 `min_gain` 才算达标。可评估对少于 2 时证据为 `insufficient`。`release_rule` 为 `any_primary` 且有 k 个主指标时，每个指标的显著性水平除以 k。置信度允许 0.8 到 0.999。
- `{"kind": "exact_measurements"}`：规格声明指标是确定性的（同样输入重复运行得到同样数值）。沿用现在的均值判定，允许只有一对样本。结果的适用范围里写明这是规格的声明，代码没有核实。

保护指标（`max_loss`、`per_pair_no_regression`）的规则不变。t 分位数用标准库实现（正则化不完全贝塔函数加二分），并用数表值做测试。

写这份设计时用临时脚本核对过这条规则（脚本不进仓库）：分位数与数表值在小数点后四位一致；两臂完全同分布、`min_gain` 为 0 时，在 2 到 16 对样本下，现有规则约 50% 判为达标，新规则约 5%。

**对现有规格的影响。** 增益完全一致的多对样本结果不变（标准差为 0 时下界等于均值）。只有一对样本、又没有声明 `exact_measurements` 的规格，结算结果从 `met` 变为 `insufficient`，不会报错，试验锁照常释放。仓库里三处单对样本的规格（`rsi_domains/tabular/demo.py`、`tests/generic/test_mechanisms.py`、`tests/v2/test_branches.py`）的指标都是确定性的，加上声明后结果不变。

## 6. 测试计划

测试放在 `tests/v2/`，复用 `tests/v2/liveness_support.py` 的 `open_run`、`Scripted`、探针适配器。全部使用脚本化的角色响应，不调用模型。每个测试结尾 `verify_history`。

**效果信号**（`test_orchestration_signal.py`）

- 配置校验：未登记的键、越界的值、空的阈值表被拒绝；`init` 路径同样拒绝。
- 步骤分类：结果、被拒、工具拒绝输入、工具失败、无动作、服务失败各一例；最终复核与未派发的调用不计。
- 新结果按内容去重；重复请求的判定，包括“工具失败后重试不算重复”。
- 窗口：越线时写入事实并创建发现 Work，Meta 发现的请求包里有完整的事实；没有越线时只写事实。
- 窗口里有未知 Effect 时不结算，对账后结算。
- 次数用尽、已有正在处理的编排 Issue 时只记为待唤醒；该 Issue 关闭后，仍然成立的信号被唤醒，已不成立的标为失效；没有人接手的 Issue 不阻止唤醒。
- 停机：Lab 两次被拒后，同一次 `run_until_wait` 里 Meta 发现运行；Lab 请求的工具明确失败后同样触发；同一停机状态不重复触发；服务失败、容量阻塞与 Lab 主动结束不触发。
- 重复调用 `advance()` 不产生新事件。
- 信号事实不进入开放巡检的默认选取。

**策略与发布**（`test_orchestration_policy.py`）

- 策略校验与上限；版本哈希稳定。
- 基线下的 Lab 请求包与 Effect 都记有版本；`CodexExecutor` 在包与 Effect 版本不一致时拒绝执行。
- `propose_policy_change` 只在可提交时出现在处置 schema 中；每项接纳条件各有一个被拒用例，包括只改巡检间隔和 Lab 容量阻塞。
- 处置请求包里，越线事实作为必需证据完整交付，即使可选证据已被分页。
- 发布：指针切换；Lab 已停下时补一个步骤；下一个 Lab 请求包含有补充段、步骤记录、最近结果和版本切换说明；Issue 被挂起。回退后的下一个 Lab 请求包同样带版本切换说明。
- 结算四种情况各一例，截止时间用注入的时钟。验证 `validation` 事实进入 Issue 证据、Meta 处置被唤醒。
- 回退后已发布的科研事实仍在；回退后的下一个请求包使用基线版本。
- 崩溃重入：发布事务提交后、挂起之前中断，再次应用提议得到同一结果；结算重复调用不变。
- 巡检间隔取自当前策略。
- 端到端：§5.8 的两条路径。

- t 分位数与数表值一致。
- 两臂同分布加噪声时，旧规则约一半判为 `met`，新规则的误判比例受置信度约束（固定随机种子）。

## 9. 已知局限与后续

- **没有经过真实模型验证。** 所有测试都用脚本化响应。Meta 能否从信号事实中得出合理的诊断、写出有用的补充段，需要一次真实运行来观察。
- **过程指标可以被迎合。** Meta 可以写出让 Lab 产出许多互不相同但没有价值的结果的补充段，从而通过试用。试用发布是工程验收，不是收益证明。要判断收益，需要宿主声明进度指标，或做成对对照。
- **Lab 主动结束不触发信号。** Lab 以 `no_action` 结束而窗口未满时，要等宿主再次启动 Lab 把窗口填满才会结算。
- **请求包超出容量。** Lab 因容量阻塞时不唤醒 Meta，也不接纳策略变更，仍由操作者处理（重建会话后重新启动 Lab）。接纳条件第 7 条限制了候选能增加的字节数。试用期间如果仍然发生容量阻塞，试用立即回退，被阻塞的 Work 不会自动重排。
- **回退抹不掉会话历史。** 见 §5.7。版本归属在账本里是准确的，但模型的行为可能仍受已撤回的补充段影响，脚本化测试看不到这一点。
- **试用期间 Lab 主动结束。** 窗口填不满时要等到截止时间才回退，期间没有额外费用。
- **未启用本功能的运行。** Lab 请求的工具明确失败后，Lab 链仍会静默结束，驱动报告仍是 `quiescent`。这是前置分支的现状，本次不改默认行为，作为后续事项单独报告。
- 后续可做：工具自主构建与通用产物适配器；OS 级隔离；宿主声明的进度指标；能按策略运行 Lab 的对照执行器，并让 `settle_trial` 的结论进入版本指针；前端展示策略版本与窗口。
